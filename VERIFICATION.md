# Verification — 13 September 2026 (accounts and cloud saves)

- Twenty-eight Node tests pass (`npm test`), five of them new: the cloud store honours the same synchronous `getItem`/`setItem` contract as localStorage, a save round-trips through it unchanged, the shared character record round-trips, each language keeps its own slot, and — the rule this feature rests on — a guest session writes nothing to persistent storage at all. The twenty-three existing tests are untouched and still pass, because `learning.js` did not change.
- Row-level security verified against the live policies by acting as two separate users inside a transaction: each saw exactly one row (their own), neither saw the other's, and an insert on another player's behalf was rejected by the `WITH CHECK` clause. The `auth.users` trigger created both profile rows automatically, and deleting the test users cascaded their saves and profiles away.
- Supabase security advisors are clean for the objects added here; the one remaining warning is Supabase's own pre-existing `rls_auto_enable` event trigger, which was not touched.
- Headless Chromium (software WebGL) with **all Supabase traffic blocked**: the game boots to a playable guest session in ~1.3s with no page or console errors, the footer reads `PLAYING AS A GUEST · NOT SAVED`, "Continue your story" is correctly hidden, and a guest can create a character and walk around The Crossing. An unreachable backend is a playable state, not an error.
- Account panel checked at 1280px and 400px: sign-in, sign-up, password-reset and signed-in states render, the two actions sit on one row at both widths, and Escape closes the panel from inside a focused text field (this last one was a real bug — the global keydown handler bailed on `INPUT`, making the panel un-closeable by keyboard, and was fixed).
- **Not verified here:** no live sign-up, confirmation email, sign-in, password reset, or cloud round-trip was exercised, because this sandbox's egress policy blocks `*.supabase.co` entirely — neither curl nor the browser can reach the project. The auth and sync paths are therefore verified by unit test, schema-level policy test and code review, not end to end. That gap closes on the first real sign-up from a browser that can reach the project.
- **Blocked on configuration, not code:** email confirmation needs an SMTP sender. Supabase's built-in mailer is rate-limited to a handful of messages an hour and is explicitly not for production, and the only domain in the connected Resend account (`mylittlebot.netlify.app`) is in a `failed` verification state and cannot be fixed, since a `netlify.app` subdomain does not allow the DNS records Resend needs. A real sending domain is required before a public launch.
